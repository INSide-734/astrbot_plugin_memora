# 设计、计划与文档维护边界

**最后更新：** 2026-07-27
**适用范围：** `docs/` 及仓库内开发文档、设计文档与计划文档的归属和联动

## 职责与边界

`docs/` 保存跨模块设计、实施计划和旧链接迁移入口。本文件是 `docs/` 的局部协作入口，同时约束公开文档、设计与计划材料应放在哪里；公开中文用户与开发文档属于 `website/docs/`。

本目录承担：

- 不适合放入根级或模块级 `DESIGN.md` 的跨模块专题设计；
- 跨模块设计文档与计划材料的归属、状态和维护联动；
- 旧文档路径的简短迁移入口，以及仓库文档的链接、事实来源、时效和敏感信息边界。

本目录不承担：

- 面向安装者、使用者和贡献者的公开指南；详细中文内容属于 `website/docs/`，根级 `README.md` 只保留项目、安装和文档入口；
- 开发环境、质量门禁、调试和发布准备指南；公开中文内容属于 `website/docs/development/`；
- 项目级稳定架构总览；它属于根级 `DESIGN.md`；
- 单一模块的实现细节；它优先属于该模块的 `AGENTS.md`、`DESIGN.md` 或源码附近注释；
- 发布历史；它属于 `CHANGELOG.md`；
- 只存在于本地忽略目录、聊天或临时工具状态中的计划；需要进入仓库的材料必须转成受版本控制的文档；
- 可执行行为证明；代码、Schema、迁移、测试和质量脚本才是对应行为的权威来源；
- 构建产物、测试报告、覆盖率输出、缓存、运行时数据库或本机工作记录。

只有当前分支中实际存在的文件才能作为文档来源。README、CHANGELOG 或旧提交提到某个路径，不代表缺失文件仍然有效；不得凭引用名称复原旧结论。

## 按问题选择权威来源

| 问题 | 首要事实来源 | 文档职责 |
|---|---|---|
| 运行时行为与数据流 | 生产代码、数据库迁移、行为测试 | 解释稳定边界，不能覆盖代码事实 |
| 配置字段与默认值 | `_conf_schema.json`、Pydantic 模型、运行时读取、Dashboard 类型与契约测试 | 说明使用方式和联动面，不单独定义字段 |
| 管理命令与 API | 注册代码、请求/响应模型、契约测试 | 提供面向读者的入口、示例和限制 |
| 开发与质量门禁 | `pyproject.toml`、锁文件、`scripts/`、Dashboard scripts 与 CI 配置 | `website/docs/development/` 给出可复现命令、前置条件和结果判定 |
| 项目级稳定设计 | 根级 `DESIGN.md` | 专题文档可补充细节，但必须由稳定设计入口链接 |
| 模块级稳定设计 | 最近的模块 `DESIGN.md`、`AGENTS.md` 与实现 | 避免在 `docs/` 复制模块内部说明 |
| 拟议变更与实施任务 | 当前任务/issue；需要版本化时使用 `docs/design/` 或 `docs/plans/` | 明确标为目标状态，不能描述成已落地能力 |
| 中文用户安装、配置和使用 | `website/docs/` | 根级 README 只保留最短入口；内容与实际版本、命令和元数据保持一致 |
| 已发布变更 | `CHANGELOG.md` 与版本元数据 | 只记录已经交付的事实，不充当当前设计规范 |

文档与实现冲突时，先核对当前代码和可执行测试。确认文档过期后应在同一变更中修正文档；若实现本身违反已批准的安全、数据或兼容性约束，则先停止扩写文档，按缺陷处理，不得用改文档掩盖实现偏差。

## 文档归属规则

| 内容 | 放置位置 | 不应放置的位置 |
|---|---|---|
| 中文安装、功能、命令与运维指南 | `website/docs/` | 根级 README、`docs/` |
| 中文开发、调试与门禁指南 | `website/docs/development/` | `docs/`、测试注释、临时报告 |
| 全项目长期稳定的架构与约束 | 根级 `DESIGN.md` | 临时任务列表 |
| 单模块长期稳定的设计 | `<module>/DESIGN.md` | 根级设计的重复章节 |
| 无单一模块所有者的专题设计 | `docs/<TOPIC>.md`，并从根级设计或相关模块入口链接 | 互不引用的第二套架构总览 |
| Agent 导航、目录职责和修改联动 | 最近的 `AGENTS.md` | 普通用户文档 |
| 需要版本化评审的设计提案 | `docs/design/<YYYY-MM-DD>-<topic>.md` | 稳定设计文档中的“当前实现”章节 |
| 需要跨会话执行的实施计划与验收记录 | `docs/plans/<YYYY-MM-DD>-<topic>.md` | README、CHANGELOG 或散落的 Markdown 待办 |
| 发布记录 | `CHANGELOG.md` | 设计文档或计划文档 |
| 局部算法原因与非显然控制流 | 源码注释或函数说明 | 脱离实现的普通文档 |

同一事实只保留一个详细权威说明。其他入口使用相对链接和一段必要摘要，不复制整章内容。若一个专题已经有明确模块所有者，优先在该模块维护；只有跨模块读者确实需要统一入口时才新增 `docs/` 文档。

## 开发文档

开发文档描述当前分支上可执行的工作方式，而不是理想流程。新增或修改时应包含与主题有关的最小信息：

- 适用范围、目标读者和不包含的内容；
- 从仓库根目录开始的前置条件与精确命令；
- 命令的工作目录、重要副作用、成功判定和常见失败边界；
- 对应脚本、配置、测试或 CI 入口；
- 仅在确有运维价值时记录版本、平台或日期限制。

命令必须能从当前仓库结构推导，不得从旧日志或记忆抄写。不要把本机绝对路径、临时目录、未锁定依赖版本或只在作者机器存在的工具写成通用步骤。可选路径和降级路径必须明确标注，不能与默认流程混写。

若文档记录一次性测试或门禁结果，应同时写明日期、提交或工作树状态、完整命令、关键环境和实际结果。一次运行结果不是永久基线；新的验证结果应替换或追加为有明确状态的记录，不能让读者误认为它代表当前 HEAD。

## 设计文档

设计文档记录已经采用、需要长期约束后续实现的决策。它说明“为什么这样设计”和“哪些边界不能破坏”，不逐文件复述代码，也不承担实施任务跟踪。

根据主题选择必要章节，通常包括：

- 背景、问题和非目标；
- 组件所有权、依赖方向和关键数据流；
- 数据权威、身份、revision、scope、privacy 与生命周期不变量；
- 失败隔离、取消传播、并发、兼容和迁移边界；
- API、配置、持久化或 Dashboard 的跨层契约；
- 可执行验证入口、已接受风险和明确替代方案。

当前状态和目标状态必须分开写。尚未落地的接口、字段、目录或行为必须标为提案，不能在稳定设计文档中使用现在时伪装成现状。实现完成后，只把仍需长期维护的决策同步到根级或模块级设计；讨论过程和逐步任务留在相应的版本化设计或计划文件中。

Mermaid、表格或示例只在能显著降低理解成本时使用。图中的组件名、调用方向和边界必须能在当前代码中找到对应，不得为了图形完整而虚构抽象层。

## 计划文档

计划默认留在当前任务或 issue 中。只有需要代码评审、跨会话交接、分阶段交付或长期保留验收证据时，才新增受版本控制的计划文档；不要为小型、单文件且契约明确的修复制造额外流程。

需要先评审目标设计时使用 `docs/design/<YYYY-MM-DD>-<topic>.md`；设计获准后，需要独立执行清单时使用 `docs/plans/<YYYY-MM-DD>-<topic>.md`。只有两者确实服务于不同读者和生命周期时才同时创建，不能复制相同背景、约束和任务。

计划文件顶部至少标明状态、最后更新日期、范围以及关联设计或代码入口。状态使用“草案”“已批准”“进行中”“已完成”或“已取代”；“已取代”必须链接后继文件，“已完成”必须给出实际验证证据。

计划材料还必须：

- 区分现状、目标、非目标和待决问题；
- 将每项任务绑定到可观察结果与验证命令；
- 标出依赖顺序、数据迁移、兼容、回滚和安全影响；
- 不把未验证的完成状态、测试结果或性能结论写成事实；
- 完成后把稳定决策同步到正式设计/开发文档，并把计划标为已完成或已取代。

计划描述执行顺序和验收证据，设计描述长期约束，两者不得复制实现细节。计划不能成为永久 API、配置或架构说明；完成计划后，读者不应依赖任务勾选框才能理解当前系统。

## 修改联动

| 发生的变更 | 必须核对的文档面 |
|---|---|
| 安装方式、最低 AstrBot/Python/Node 版本或依赖变化 | 根级 README、翻译、元数据与 `website/docs/` |
| 管理命令名称、参数、权限或行为变化 | `website/docs/reference/commands.md`、CHANGELOG、根级 `AGENTS.md` 与命令测试 |
| `check_all.py`、smoke、构建或 benchmark 入口变化 | `website/docs/development/`、`scripts/AGENTS.md`、CI 和调用方 |
| 配置叶、默认值或保存语义变化 | Schema、模型、运行时、Dashboard、`website/docs/` 与契约测试 |
| API、Dashboard bridge 或分页/冲突协议变化 | 后端/前端局部上下文、专题设计和契约测试 |
| 存储、身份、隐私、Prompt 或派生数据权威变化 | 根级/模块设计、安全说明、迁移和回归测试 |
| 观测字段、指标或评测口径变化 | 对应专题文档、allowlist、数据集/基线说明和测试 |
| 版本化设计/计划完成或被取代 | 同步仍有效的稳定决策、状态和实际验证证据，修正临时交叉引用 |
| 文档移动、重命名、合并或删除 | 所有入站相对链接、导航表和 README 项目结构 |

只修改文档措辞时不要虚构代码联动；但若文档变更暴露实现或测试不一致，应单独报告并按对应模块流程处理。不要顺手重排无关章节、统一全仓格式或清理与任务无关的旧材料。

## 安全、隐私与示例数据

- 不得记录 Provider 密钥、请求头、内部 API 地址、真实数据库、用户目录或部署凭据。
- 不得把真实 query、prompt、记忆正文、身份、会话 ID、canonical ID、source mapping、revision 或 job 信息放进示例、截图和测试结果。
- 诊断和观测示例只使用仓库契约允许的标量字段与匿名占位符。
- 错误示例不得粘贴原始堆栈或第三方响应中的敏感内容；保留复现所需的最小错误类型和安全摘要。
- 截图、报表、基准输出和生成站点默认视为产物；只有任务明确要求版本化且内容已脱敏时才能提交。

## 编写与维护流程

1. 先阅读根级及目标模块的 `AGENTS.md`，定位代码、测试和脚本中的权威入口。
2. 判断内容属于 `website/docs/`、README 入口、根/模块 `DESIGN.md`、版本化设计/计划还是 CHANGELOG，避免创建平行来源。
3. 只写当前任务需要的章节；引用已有详细说明，不复制它。
4. 对每个行为陈述核对当前实现，对每条命令核对真实入口和工作目录。
5. 修改行为时在同一变更中同步受影响文档；纯文档变更只运行与文档本身相称的检查。
6. 完成前检查物理行数、相对链接、Markdown 结构、敏感信息和工作树差异。

## 验证要求

普通文档变更至少执行：

```powershell
git diff --check
(Get-Content docs/AGENTS.md).Count
```

还必须逐一确认本轮新增或修改的相对 Markdown 链接能够从源文件目录解析。Markdown 设计/计划文件不得超过根级约定的 400 个物理行；普通说明也应保持可审阅，不能通过超长行规避限制。

只有文档中的可执行契约发生变化时才运行对应测试、构建或 smoke。例如修改门禁命令应运行相关脚本检查；只补充维护边界不要求启动后端、Dashboard 或完整仓库门禁。不得用一次窄测试结果声称未运行的全量门禁通过。

扫描和校对时跳过 `node_modules/`、`dist/`、`build/`、覆盖率输出、缓存、二进制、运行时数据、工作树和 Dashboard 生成物；这些内容不能作为架构或文档事实来源。
